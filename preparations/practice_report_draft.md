## Введение

Одной из ключевых проблем при разработке автономных IoT-устройств с голосовым
управлением является высокое энергопотребление систем распознавания речи.
Традиционные облачные решения (Google Assistant, Яндекс Алиса) требуют
постоянного подключения к сети и передачи аудиоданных, что делает их
непригодными для автономных устройств с батарейным питанием. Специализированные
ASIC-чипы (Syntiant NDP101, Ambiq Apollo) обеспечивают минимальное потребление,
однако недоступны для независимой разработки и не позволяют гибко изменять
функциональность.

Настоящая работа посвящена разработке прототипа системы распознавания голосовых
команд на базе микроконтроллера ESP32-S3 с квантизированными нейронными сетями и
аппаратным управлением питанием периферии. Целью является снижение среднего тока
потребления в режиме ожидания за счёт отключения микрофона INMP441 (1.4 мА)
через MOSFET-ключ при нахождении системы в режиме глубокого сна.

## 1. Этап 2: Проектирование системы

### 1.1 Обзор предметной области

В ходе анализа предметной области были рассмотрены три основных подхода к
реализации голосового управления на IoT-устройствах:

**Облачные решения** (Google Speech-to-Text, Яндекс SpeechKit): аудио с
микрофона передаётся на серверы через WiFi/LTE, распознавание выполняется в
облаке. Недостатки: зависимость от интернета, задержка 300–1500 мс, отсутствие
приватности, высокое потребление на передачу данных (~100–300 мА при активном
WiFi).

**Специализированные ASIC** (Syntiant NDP101, Ambiq Apollo4): чипы разработаны
исключительно для задачи keyword spotting, потребляют единицы микроватт при
инференсе. Недостатки: высокая стоимость, закрытая экосистема, недоступность для
независимых разработчиков, фиксированная функциональность.

**Edge AI на МК общего назначения**: квантизированная нейронная сеть запускается
непосредственно на микроконтроллере. Подход, реализуемый в данной работе.
Преимущества: доступность компонентов (~300 руб. за ESP32-S3), открытая
экосистема разработки (ESP-IDF, ESP-SR), возможность кастомизации.

Выбор платформы ESP32-S3 обоснован следующими характеристиками:

- Двухъядерный процессор Xtensa LX7 240 МГц с поддержкой SIMD-инструкций для
  ускорения нейросетевого инференса
- Аппаратный I2S-контроллер для прямого подключения MEMS-микрофонов без внешних
  кодеков
- ULP-сопроцессор для работы в режиме ультранизкого потребления
- Поддержка внешней PSRAM (до 8 МБ) для хранения весов нейронных сетей
- Зрелая экосистема: ESP-IDF, ESP-SR (WakeNet, MultiNet), ESP-DL

### 1.3 Архитектура системы

Для точного измерения энергопотребления применена архитектура с двумя
изолированными доменами питания:

- **Домен №1 (измеряемая система):** ESP32-S3 + INMP441 — исследуемая система
- **Домен №2 (измерительный):** ESP32-C3 + INA219 — логгер данных

Раздельное питание исключает влияние импульсных помех WiFi/BLE модуля ESP32-C3
(до 300 мА пиково) на измерения тока в домене №1.

```
[Домен №1]                          [Домен №2]
18650 → TP4056 → INA219 → ESP32-S3  |  18650 → TP4056 → ESP32-C3
                INMP441 (I2S) ↑     |       INA219 ←→ (I2C) ESP32-C3
                                    |       ESP32-C3 → USB → PC
```

### 1.5 Электротехнический расчёт

#### Потребление по компонентам и режимам

| Компонент          | Active (inference) | Light Sleep | Deep Sleep   |
| ------------------ | ------------------ | ----------- | ------------ |
| ESP32-S3 (ядра)    | ~40–60 мА          | ~0.8 мА     | ~0.01 мА     |

| WS2812 LED (пик)   | ~20 мА             | 0           | 0            |
| **Итого домен №1** | **~75–80 мА**      | **~2.2 мА** | **~1.41 мА** |

**Ключевое наблюдение:** в режиме Deep Sleep ESP32-S3 потребляет ~10 мкА, однако

делает Deep Sleep неэффективным без физического отключения питания микрофона.

### 2.1 Описание стенда

Тестовый стенд выполнен на двусторонней макетной плате, закреплённой на
основании из оргстекла на латунных стойках M4. Два домена питания физически

собственный аккумулятор 18650 и модуль защиты TP4056.

Для быстрой замены модулей ESP32-S3 и ESP32-C3 установлены гребёнки pin headers.
Тумблеры обеспечивают независимое включение каждого домена. LED-индикаторы
показывают активность доменов.

### 2.2 Проблемы при сборке и их решение

**Проблема 1: GPIO9 как strapping pin ESP32-C3**

При подключении INA219 к GPIO8/GPIO9 (SDA/SCL) ESP32-C3 переставала определяться
как USB CDC устройство. Причина: GPIO9 является strapping pin — при низком
уровне на нём во время старта чип переходит в download mode. INA219 во время
инициализации I2C тянула SCL (GPIO9) к нулю, что интерпретировалось как команда
входа в bootloader.

Решение: перенесены линии I2C на GPIO0 (SCL) и GPIO1 (SDA) — они не являются
strapping pins на ESP32-C3.

**Проблема 2: Потери напряжения на земляных соединениях**

При первых измерениях обнаружено расхождение ~70 мВ между показаниями INA219
(bus voltage) и мультиметром на пинах ESP32-S3. Причина: земляные шины были
соединены через несколько последовательных джамперов китайского производства с
суммарным сопротивлением ~1 Ом, что при токе 78 мА давало падение U = I·R =
0.078·1 ≈ 78 мВ.

Решение: все земли переразведены по топологии «звезда» — единая точка соединения
земель выведена в угол платы, от неё короткими медными перемычками запитаны все
земляные узлы. Также заменены тонкие провода в держателях аккумуляторов на более
толстые. После переразводки расхождение составило 5–6 мВ (в пределах погрешности
INA219).

## 3. Этап 4: Разработка ПО и эксперименты

### 3.1 Прошивка основного домена (ESP32-S3)

#### Среда разработки

Использован PlatformIO с фреймворком ESP-IDF v5.4.0. Редактор — Neovim с LSP
(clangd). Конфигурация clangd требует явного указания compilation database и
исключения неподдерживаемых флагов компилятора (`-mlongcalls`,
`-fstrict-volatile-bitfields`), а также явного указания путей к заголовочным
файлам компонентов ESP-IDF.

#### Аудиопайплайн

Путь сигнала от микрофона до нейросети:

```
INMP441 → I2S DMA (int32, 16кГц) → конвертация → WakeNet9 (int16)
```

**Особенности реализации драйвера INMP441:**

1. _Формат данных:_ INMP441 выдаёт 24 значимых бита в 32-битном слове
   (MSB-justified). Экспериментально подобран сдвиг `>> 12` для получения
   корректного int16.

2. _Чередование каналов:_ ESP32-S3 в режиме `I2S_SLOT_MODE_MONO` передаёт данные
   парами L+R в DMA-буфер (R=0). Фикс: чтение `samples×2` int32, выборка только
   чётных индексов.

3. _DMA-буферы в DRAM:_ GDMA не имеет доступа к PSRAM, поэтому буферы I2S
   обязаны располагаться во внутренней SRAM.

#### Интеграция WakeNet9

ESP-SR предоставляет предобученные квантизированные (INT8) модели keyword
spotting через компонент `espressif__esp-sr`. Веса моделей хранятся в отдельном
SPIFFS-разделе Flash (1138 КБ для 4 моделей). Инициализация:
`esp_srmodel_init("model")` монтирует раздел и возвращает список доступных
моделей.

Реализована детекция 4 wake words: Alexa, Hi ESP, Jarvis, Computer. При
срабатывании — световая индикация через WS2812 RGB LED (каждая команда — свой
цвет).

#### Ограничения памяти

Плата ESP32-S3 Zero (FH4R2): Flash 4 МБ, PSRAM 2 МБ. Полный стек ESP-Skainet
(AFE + WakeNet9 + MultiNet4) требует ~2066 КБ PSRAM при доступных 2048 КБ.
Принято решение использовать только WakeNet9 без AFE и MultiNet — это покрывает
цели работы по исследованию энергопотребления.

> **Примечание:** заказана плата ESP32-S3 N8R8 (8 МБ Flash + 8 МБ PSRAM),
> позволяющая запустить полный стек.

### 3.2 Прошивка измерительного домена (ESP32-C3)

#### Архитектура модулей

```
main.c
├── i2c_bus.c / .h    — инициализация I2C шины (новый API driver/i2c_master.h)
└── ina219.c / .h     — драйвер датчика тока
```

#### Драйвер INA219

Взаимодействие с INA219 осуществляется через I2C (адрес 0x40, частота 100 кГц).
Протокол: запись регистра — транзакция
`[S][addr W][ACK][reg][ACK][MSB][ACK][LSB][ACK][P]`; чтение —
`[S][addr W][ACK][reg][ACK][Sr][addr R][ACK][MSB][ACK][LSB][NACK][P]`.

Конфигурация INA219:

- CONFIG = 0x399F: диапазон шины 32 В, PGA÷8 (шунт ±320 мВ), 12-bit ADC,
  непрерывное измерение
- CALIB = 4096: Cal = 0.04096 / (Current_LSB × R_shunt) = 0.04096 / (0.0001 ×
  0.1)
- Current LSB = 0.1 мА

Вывод: CSV в UART с частотой 10 Гц. Формат: `bus_v,current_ma,shunt_mv`

#### Проблемы при разработке

При использовании устаревшего API (`driver/i2c.h`) компилятор выдавал
предупреждения о deprecated функциях. Переход на новый API
(`driver/i2c_master.h`, ESP-IDF ≥ 5.x) с bus-device моделью.
